# Report and summary evaluation records

New summary preparations create an `evaluationRuns` record for the summary and one for each report-reading attempt. This is local PDF extraction/OCR and comparison, not a remote language-model call.

Each record keeps the browser session, original report IDs, original storage IDs, filenames, content types, content hashes when available, engine label, start/end times, and running/succeeded/failed status. Successful outputs are JSON files in Convex storage referenced by `outputStorageId`. Reading outputs contain the extracted report; summary outputs contain the comparison, selected test keys and finished summary HTML. Failed attempts keep their error message. Old preparations are not reconstructed.

`evaluations.get` requires the same browser session and returns an output download URL only for that session. The Convex dashboard can inspect the table. Original files remain unchanged. Pending inputs and completed outputs are saved in this browser’s IndexedDB and retried after 1, 2, 4, 8, 16, 32, then at most every 60 seconds. Going online or reopening the app also resumes delivery. A per-session retry key reuses the same Convex record, and completed outputs are never overwritten by retries. Logging failures are reported to the browser console and do not prevent report reading. Clearing browser data removes pending records. If browser storage is unavailable, retries continue in memory but cannot survive closing the page. Closing before report reading finishes can leave a running record without an output; retries cannot recreate an unfinished analysis.

## Local real-report layout audit

Run `node tests/reference-layout-audit.mjs` to inspect the PDFs already in `references/` through the production PDF reader, including local scan recognition. An optional directory argument selects another local folder. This is an exploratory audit, not an expected-results test: rejected layouts are reported, not counted as successes. It checks numeric outputs and source-page/row consistency, and attempts comparison using the existing patient/date/unit rules. Output lists filenames, counts and layout status only; it does not publish patient identities, dates, values or PDF contents. Original personal files and intermediate inspection files remain ignored by git.

The October 2026 run read two Apollo files (59 and 65 extracted markers) and one Tata 1mg file (51 markers); a comparison had 63 tests present in at least two reports. This does not mean every result or every page was supported. Non-table pages and attachments were excluded, including the scanned attachment in the long Apollo file. Both Practo/Thyrocare files were rejected. Those layouts use footer collection dates and separate reference blocks rather than the existing dated, row-based reference-column layout. Source-page images were reviewed for selected blood-count rows; this was a spot check, not a complete independent verification of every result. No application reading rules were changed by this audit.

## Footer-date / separate-reference support

The reader now supports explicit `Sample Collected on (SCT)` dates, split colon/name fields with the printed age/sex suffix, `TECHNOLOGY` and `NORMAL RANGE` headers, result names above the numeric row, and separate `Reference Range:` blocks. Collection dates are required; release dates are never substituted. Multi-category or sex-specific blocks remain source text with unknown range status. Adjacent guidance for known diabetics is excluded from the reference. Missing ranges remain missing, and source coordinates identify the numeric result row.

`tests/footer-layout.test.mjs` checks these boundaries, missing/invalid collection dates, next-test boundaries, and existing mixed-patient/mixed-date rejection. `tests/fixtures/footer-summary.expected.json` plus `footer-sample-{january,july}.pdf` check the complete summary against fictional independent values. Recreate them with `scripts/create-footer-eval-fixtures.py`. The local audit now reads both existing Practo files with 59 extracted markers each; the Apollo/Tata counts remain unchanged. The two Practo files share a collection date, so they must not be compared together as different dates. Reading support does not imply every possible result format is supported. Personal files remain local and uncommitted.

## Multiple panels and verified name variants

The dated-table reader now resumes after comments only at a complete repeated table header (using that header’s column order), or an explicit supported panel caption with nearby numeric rows in the established columns. Recognized captions include liver, basic iron studies, complete blood count, kidney/renal and lipid panels. Prose and numeric examples without a new panel or table header remain excluded. Unsupported captions are not guessed. `tests/multiple-panels.test.mjs` protects these boundaries; `tests/fixtures/panels-summary.expected.json` checks a full summary from fictional PDFs, including exclusion of fake numeric notes and correct physical pages. Recreate them with `scripts/create-panels-eval-fixtures.py`.

Explicit full names/acronyms now match for PCV/HCT, MCV, MCH, MCHC, RDW-CV, MPV, PDW, lymphocyte percentage, absolute differential counts, total thyroid hormones, TSH, BUN and the printed liver-enzyme acronyms. Matching still requires compatible units. `X 10³ / μL`, `X 10^3/uL` and `10^3/μL` are equivalent notation for the same count scale; normalization does not multiply or change a result. Different powers, raw cells/uL, T3 ng/dL versus ng/mL, and the unclear printed `pq` versus `pg` remain separate. Direct versus unspecified cholesterol measurements are not merged.

The local real Practo–Tata audit now extracts 65 Tata markers instead of 51 and finds 39 matching tests instead of 14. Spot checks confirm the restored iron and liver results on physical pages 26 and 24. This is sample-specific coverage, not a guarantee for all lab reports. Originals and personal comparison files remain local and ignored by git.

## Per-file failures and OCR rejection evidence

Every selected file is attempted, including after a download or reading failure. Failed files are named in the Summary page with a plain explanation and remain excluded from result values. If only one file reads successfully, its results can be summarised with no trend or comparison claim. Zero readable files produce no summary. Normal multi-report comparison rules remain unchanged.

Both OCR confidence checks retain the strict below-80 rejection rule. Their errors now include structured diagnostics: page, field, threshold, and every rejected word’s exact text, score and bounding box. Only the OCR error wrapper propagates this metadata; the native text-PDF extraction path is unchanged. The existing failed `evaluationRuns` record keeps the error and references a JSON output containing diagnostics. The same retry queue persists this JSON offline. Failed logs without OCR confidence metadata retain their previous error-only format.

The `confidence-partial` finished-summary case selects a genuine low-confidence fictional image-only PDF before a good fictional text PDF. Real Tesseract recognition rejects the scan; the good file still produces exact independently expected values with source links and no invented trend. `scripts/create-confidence-eval-fixture.mjs` reproduces the scan by blurring only the fictional name and verifies genuine OCR rejection before saving it. `tests/ocr-page.test.mjs` checks both rejection fields and acceptance at exactly 80. The logging retry test and explicit live integration check verify preservation of scores and failed status.

## Scan vision fallback

Native text PDFs keep their existing PDF.js/parser path. Each scanned page gets local Tesseract OCR before any possible vision request. `scanPageCheck` looks for numeric results beside lab units or reference-range-like numbers; it ignores cover metadata such as dates, ages, phone numbers and page numbering. Pages without that evidence are skipped before AI. Screening never supplies biomarker values or relaxes the unchanged 80% OCR acceptance rule. Low-confidence or unsupported OCR tables with test-like content can fall back to OpenAI `gpt-4.1-mini`, through `vision.read` in Convex only. Timeouts without an OCR screening result do not trigger vision.

Each summary preparation shares one `visionReadings` record across its selected files. Atomic server reservations cap it at 30 vision pages. `visionAppDaily`, indexed by IST calendar day, enforces a hard 150-page daily cap shared by all users on the deployment. Failed provider attempts consume reservations. The initial global counter includes that day's previous reservations from the old `visionDaily` counters, read through a bounded day index; it never resets spending to zero on migration. There is no separate ten-call user cap. Limits or API failures stop preparation with a clear visible message.

The screen and reading logs retain per-file `scanCoverage`: number checked, pages actually included, how many came from vision or local OCR, and each skipped physical page with its reason. Failed readings retain their available coverage too. Pages where OCR finds no test-like content are described as OCR omissions, with a reminder to check originals; they are never asserted to contain no medical results with certainty.

Every provider attempt creates a server-owned `evaluationRuns` entry containing the original report reference. Saved JSON contains the rendered-page storage ID, page number, OCR rejection evidence, exact prompt/schema/request, raw provider response and structured result or error. Unreadable values remain null and are excluded from comparisons. Accepted values retain physical page references and `readPath: "vision"`; displayed results carry “read from scan, please check against the original.” Patient identity and valid printed dates must agree. No reference range is invented when absent.

`tests/fixtures/scan-filter-sample.pdf` is an entirely fictional 27-page image-only report: 26 covers/image attachments, followed by known haemoglobin 13.2 g/dL, CRP 3.0 mg/L and Vitamin D 24 ng/mL on physical page 27, dated 15 July 2026. The ordinary suite uses real local OCR, screening, reader, comparison and renderer with a fixed vision transport response; it verifies only page 27 reaches vision and the UI lists all 26 skip reasons. `VISION_TEST_CONVEX_URL=https://elegant-schnauzer-503.convex.cloud npm run test:vision` separately checks every physical page with real OCR and makes exactly one actual Convex/OpenAI call. Actual server reservation handlers are tested against isolated in-memory database transports for the 30/31 and shared 150/151 boundaries, earlier-day migration and blocking before provider IO. Live boundary tests deliberately do not exhaust the real app-wide daily budget. Fictional integration uploads move to their isolated session's restorable trash afterward.
